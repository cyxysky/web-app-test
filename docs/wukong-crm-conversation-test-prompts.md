# 悟空 CRM：Web Test 对话式测试 Prompt

## 使用方法

每个模块建议单独新建一个 Web Test 对话。把“公共执行规则”和一个“模块任务”一起发送给 AI。一次只执行一个模块，完成后再开始下一个模块。

测试地址统一使用 http://localhost/ 。当前系统已经初始化，并存在管理员登录会话。若执行浏览器没有继承登录状态，AI 应报告阻塞并等待人工登录，不得猜测、读取或输出密码。

建议执行顺序：

1. 系统管理基础配置
2. 产品
3. 线索转化
4. 客户、联系人与公海
5. 商机、合同、回款、发票与回访
6. 审批与任务
7. OA
8. 项目管理
9. 人力资源
10. 角色、菜单、按钮与数据权限
11. 商业智能与全局回归

## 公共执行规则（每个模块都要附带）

测试目标：

悟空 CRM 11.0 本地测试环境  
http://localhost/

账号：
12312312312
A123456

执行标识：

开始测试时生成唯一标识 RUN_ID，格式为 AIQA_YYYYMMDD_HHmmss。  
本轮新建的名称、标题、编号、备注等文本统一以 RUN_ID 开头，例如 AIQA_20260828_223000_线索01。  
手机号、邮箱、编号必须基于 RUN_ID 生成唯一且格式合法的值。

测试任务：

1. 先读取当前页面、菜单、字段、按钮和系统配置，确认本模块在当前开源版本中实际可用的能力。
2. 根据业务需求自行分析业务规则，先输出完整测试用例，尚未生成用例前不要修改业务数据。
3. 用例必须覆盖：
   - 主业务流程
   - 必填项
   - 字段长度、格式和边界值
   - 重复数据
   - 页面返回、刷新和重复提交
   - 状态流转
   - 关联关系
   - 数据持久化
   - 搜索、筛选、排序、分页和列表展示
   - 当前登录角色的功能权限
4. 每条测试用例必须包含：
   - 编号
   - 场景
   - 前置条件
   - 测试数据
   - 操作步骤
   - 预期结果
   - 优先级（P0/P1/P2）
5. 用例生成后，立即通过浏览器实际执行所有 P0、P1 用例；P2 只生成，不执行。
6. 执行时必须按用例编号逐条进行，每执行一步记录：
   - 步骤
   - 预期结果
   - 实际结果
   - 结果状态（通过/失败/阻塞）
7. 页面操作后必须通过可见页面证据验证结果。涉及新建、编辑或状态变化时，还要刷新页面或重新进入详情，验证数据已持久化。
8. 禁止仅根据“保存成功”提示判定通过；必须同时核对列表、详情、关联页签或统计中的最终状态。
9. 对保存、提交、审批等操作测试连续点击或刷新时，只操作本轮 RUN_ID 数据，避免影响已有数据。
10. 若字段、按钮、流程或菜单与业务需求不一致，先检查是否由权限、开源版本或系统配置导致，不得直接判定为缺陷。
11. 发现问题后输出：
    - Bug 标题
    - 所属模块
    - 严重程度（阻断/严重/一般/轻微）
    - 前置条件
    - 复现步骤
    - 预期结果
    - 实际结果
    - 截图证据
    - 关联测试用例编号
12. 问题必须区分：
    - 确认缺陷
    - 疑似缺陷
    - 需求与系统配置不一致
    - 开源版本不支持
    - 登录或权限阻塞
    - 环境或历史数据干扰
13. 最后输出模块测试报告，包含：
    - 环境地址和执行时间
    - RUN_ID
    - 用例总数及 P0/P1/P2 数量
    - 已执行、通过、失败、阻塞数量
    - 缺陷汇总
    - 未测试范围及原因
    - 本轮创建的数据清单

禁止事项：

- 不测试批量删除。
- 不删除或禁用当前管理员。
- 不修改当前管理员的密码、手机号、角色和部门。
- 不发送真实短信、邮件、外呼或第三方通知。
- 不进行压力测试、安全攻击、SQL 注入、XSS、路径遍历等攻击性测试。
- 不调用 Docker、数据库、服务器文件或后台管理接口绕过页面。
- 不修改非 RUN_ID 数据。
- 不自动清理失败现场；保留数据供复现。需要清理时，只列出本轮数据并等待人工确认。

## 模块 01：线索创建与转化

业务需求：

1. 销售人员可以创建一条线索。
2. 线索应包含线索名称、客户名称或公司、手机、电话、邮箱、来源、负责人、地址、备注及当前页面支持的自定义字段。
3. 线索名称及页面标记的字段必须满足必填校验。
4. 手机、电话、邮箱等字段应进行格式校验，超长文本不应导致页面异常或数据被静默截断。
5. 使用相同手机号、电话、邮箱或客户名称创建线索时，应按当前查重配置给出提示或允许用户明确处理。
6. 有效线索可以转化为客户；如果当前版本支持同时创建联系人或商机，也要验证对应选项。
7. 转化页面应自动带出能够映射的线索信息。
8. 转化完成后，原线索应显示为已转化或从未转化列表中移出，且不能重复转化。
9. 新生成的客户、联系人、商机应建立正确关联。
10. 用户可以通过关键词、负责人、时间和状态找到本轮线索。
11. 返回列表、浏览器刷新和重复点击保存/转化不得产生非预期重复数据。

重点验证：

- 新建线索主流程
- 只填写最小必填字段
- 手机、电话、邮箱合法和非法格式
- 名称、备注和地址长度边界
- 重复手机号、重复邮箱和重复客户名称
- 保存按钮重复点击
- 新建后刷新及重新进入详情
- 编辑线索并验证操作记录
- 线索转客户
- 当前版本支持时转联系人和商机
- 转化字段映射
- 原线索状态
- 新实体关联关系
- 已转化线索重复转化
- 列表搜索、筛选、排序和分页

## 模块 02：客户、联系人、跟进与公海

业务需求：

1. 用户可以创建、编辑、查看和搜索客户。
2. 客户名称、负责人及页面标记的字段满足必填规则。
3. 相同客户名称、手机号或其他查重字段应按系统配置提示重复。
4. 客户详情应正确展示基础资料、联系人、商机、合同、回款、跟进记录和操作记录等可用页签。
5. 用户可以在客户下新建联系人，并设置主要联系人。
6. 联系人姓名、手机、电话、邮箱、职务及所属客户应正确保存。
7. 用户可以新增包含文本、下次联系时间和附件的跟进记录。
8. 客户转移负责人或添加团队成员后，详情中的负责人和协作信息应更新。
9. 如果当前环境已配置公海，客户可以按规则放入公海、领取和分配。
10. 公海领取后客户负责人、领取记录和列表归属应正确，不得被重复领取。
11. 页面刷新、返回、重复保存不得产生重复联系人或跟进记录。

重点验证：

- 客户最小字段和完整字段新建
- 客户名称及联系方式边界
- 客户查重
- 客户编辑与持久化
- 客户列表搜索、组合筛选、排序和分页
- 客户详情页签及数量
- 联系人新建、编辑、查重和主要联系人
- 联系人与客户关联
- 跟进记录及下次联系时间
- 跟进记录刷新持久化
- 客户负责人转移
- 客户团队成员
- 公海入口、放入、领取和重复领取
- 公海功能未配置时的提示与问题分类

## 模块 03：产品

业务需求：

1. 管理员或有权限用户可以创建产品分类和产品。
2. 产品应支持名称、编码、分类、单位、标准价格、描述、状态及页面提供的其他字段。
3. 产品名称、产品编码和价格应满足必填、唯一性、格式和数值边界规则。
4. 产品分类层级、排序和产品归属应正确。
5. 产品创建后可在商机或合同的产品选择器中被找到。
6. 停用或下架产品后，历史业务引用仍可查看，新业务是否可选应符合系统规则。
7. 搜索、筛选、刷新和重复保存不得产生重复产品。

重点验证：

- 一级和二级产品分类
- 产品最小字段和完整字段
- 重复产品编码和名称
- 价格为 0、负数、大数和多位小数
- 名称、编码和描述长度边界
- 产品编辑与刷新
- 产品状态切换
- 分类筛选、关键词搜索、排序和分页
- 商机/合同产品选择器中的可见性
- 重复点击保存

说明：

本模块不得删除已经被商机或合同引用的产品。若测试删除限制，只验证页面是否阻止操作，不要确认最终删除。

## 模块 04：商机、合同、回款、发票与回访

业务需求：

1. 用户可以在客户下创建商机，填写商机名称、商机组、阶段、预计金额、预计成交日期、负责人和产品。
2. 商机阶段、成功概率、金额和看板位置应保持一致。
3. 商机可以正常标记赢单或输单；输单原因按页面规则填写。
4. 用户可以基于客户或商机创建合同，合同编号应唯一，客户、商机、产品、金额和日期关联正确。
5. 若合同需要审批，应进入正确审批状态；未配置审批流时要分类为配置不一致，不直接报缺陷。
6. 合同下可以创建多期回款计划，计划金额与合同金额关系应符合系统规则。
7. 用户可以创建回款并关联回款计划；合同已回款、未回款和计划状态应正确更新。
8. 当前版本支持时，可以创建发票申请和客户回访。
9. 金额、日期、编号、状态和关联关系在刷新后必须持久化。
10. 重复提交不得生成重复合同、回款、发票或回访。

重点验证：

- 商机最小字段和完整字段
- 商机阶段推进、回退、赢单和输单
- 商机金额边界及产品金额计算
- 商机看板与列表状态一致
- 合同新建、编号、金额和日期校验
- 合同与客户、商机、产品关联
- 合同审批入口及配置差异
- 回款计划单期、多期、合计不足和合计超额
- 回款新建、部分回款和金额累计
- 回款与合同、计划关联
- 发票申请及累计开票金额
- 回访计划、完成和取消
- 搜索、筛选、刷新及重复提交

执行限制：

- 不执行真实作废或批量删除。
- 审批操作只处理本轮 RUN_ID 创建的数据。
- 若审批会通知其他真实用户，停止该步骤并标记阻塞。

## 模块 05：审批与任务

业务需求：

1. 用户可以在“任务/审批”中查看待办、已办、我发起的审批以及任务。
2. 只对当前环境已有且不会通知真实第三方的审批类型进行测试。
3. 发起审批时，必填字段、金额、日期、附件和审批人应按表单规则校验。
4. 审批提交后，状态、流程节点、审批人和操作记录应正确。
5. 当前登录账号同时具备发起和审批能力时，可以测试同意、拒绝、撤回；否则标记权限阻塞。
6. 同一审批待办不能被重复处理。
7. 用户可以创建任务并设置标题、负责人、参与人、开始/截止时间、优先级、描述和关联业务。
8. 任务完成、重开、评论、附件、子任务及提醒应按当前版本能力工作。
9. 任务列表、待办数量和详情状态应保持一致。

重点验证：

- 审批列表分类和数量
- 审批表单必填、格式和边界
- 审批发起与刷新持久化
- 同意、拒绝、撤回和重复处理
- 无审批流、无审批人或无权限时的问题分类
- 任务最小字段和完整字段
- 开始时间晚于截止时间
- 任务负责人、参与人和业务关联
- 任务完成、重开和重复完成
- 子任务、评论和附件
- 任务搜索、筛选和列表状态

执行限制：

- 不创建或修改全局审批流。
- 不代替未知真实用户审批。
- 不测试会签、转交或加签，除非当前页面明确支持且参与人都是本轮测试账号。

## 模块 06：OA 日志、日历、公告与通讯录

业务需求：

1. 用户可以创建工作日志，填写日志类型、内容、接收人及当前页面支持的关联业务。
2. 日志保存后应出现在对应列表和接收范围中，刷新后数据不丢失。
3. 当前账号具备条件时，可以添加和查看评论。
4. 用户可以创建日程，设置标题、开始时间、结束时间、参与人、提醒和描述。
5. 日程开始时间不能晚于结束时间，跨天和全天日程应正确显示。
6. 日历月、周、日或当前版本提供的视图应展示一致数据。
7. 当前账号有权限时，可以创建公告草稿；不得向真实用户发布公告。
8. 通讯录应按部门和人员展示，可按姓名搜索；敏感信息展示遵循当前权限。
9. 页面返回、刷新和重复提交不得生成重复日志或日程。

重点验证：

- 日报/周报或当前日志类型
- 日志必填、长度和保存
- 日志列表、详情、评论和关联业务
- 日程最小字段和完整字段
- 非法时间、跨天、全天和过去日期
- 日历视图、日期跳转和刷新
- 日程编辑和取消
- 公告草稿必填、富文本和附件
- 公告发布按钮只检查可用性，不执行真实发布
- 通讯录部门树、人员搜索和详情

执行限制：

- 不发布会通知全员或真实用户的公告。
- 不发送日志、日程或提醒给未知真实用户。
- 如系统必须选择接收人，只选择当前管理员自己；无法选择自己则标记阻塞。

## 模块 07：项目管理

业务需求：

1. 用户可以创建项目，填写名称、描述、负责人、成员、可见范围及当前版本支持的字段。
2. 项目名称和页面标记字段满足必填与长度规则。
3. 项目下可以创建任务列表并调整顺序。
4. 任务列表下可以创建任务、子任务、检查项、标签、评论和附件。
5. 任务可以在列表之间移动，负责人、截止时间、优先级和完成状态正确保存。
6. 项目看板、任务列表、我的任务和项目动态应保持一致。
7. 项目归档后应按系统规则变为只读或从活动项目中移出。
8. 刷新、返回和重复保存不得产生重复项目、任务或评论。

重点验证：

- 项目最小字段和完整字段
- 项目名称重复和长度边界
- 项目成员及可见范围
- 任务列表新建、排序和刷新
- 任务、子任务和检查项
- 任务时间、优先级、负责人和标签
- 任务评论和附件
- 任务完成、重开和重复完成
- 任务跨列表移动
- 看板、列表、我的任务和动态一致性
- 项目归档及恢复入口

执行限制：

- 成员优先选择当前管理员自己。
- 不删除已有项目。
- 只归档和恢复本轮 RUN_ID 项目；若恢复不可用，保留现场并报告。

## 模块 08：人力资源

业务需求：

1. 先识别当前开源版本实际开放的人力资源菜单，包括员工、组织、招聘、薪资、社保、绩效或其他可见功能。
2. 只测试当前页面可用且不影响真实员工的数据。
3. 用户可以创建测试员工档案，填写姓名、工号、手机号、部门、岗位、入职日期及页面支持的字段。
4. 工号、手机号、证件号等唯一字段应进行重复校验。
5. 员工档案编辑、搜索、筛选、刷新和详情展示应正确。
6. 当前版本支持时，可以创建测试招聘职位和候选人，验证候选人阶段流转。
7. 薪资、社保和绩效属于敏感模块，只验证页面可达、表单规则和本轮测试数据；不得查看或修改已有员工敏感数据。
8. 离职操作只允许作用于本轮创建的测试员工，并且在最终确认前停止，不实际提交。

重点验证：

- HRM 菜单与开源版本能力识别
- 测试部门/岗位选择
- 员工最小字段和完整字段
- 工号、手机号等重复数据
- 日期、证件和文本长度边界
- 员工编辑、搜索、筛选和刷新
- 员工详情页签
- 招聘职位和候选人
- 候选人阶段流转
- 薪资、社保和绩效入口及权限
- 空数据页面和错误提示

执行限制：

- 不查看、截图或输出已有员工的身份证、银行卡、薪资等敏感数据。
- 不发布工资条，不计算真实员工工资，不办理真实员工离职。
- 不修改已有部门、岗位、薪资、社保或绩效方案。

## 模块 09：系统管理、组织、用户与角色

业务需求：

1. 管理员可以查看系统管理中的组织架构、用户、角色、菜单权限、系统配置、字段配置和操作日志等当前可用功能。
2. 可以创建 RUN_ID 测试部门、测试角色和测试用户，但不得修改当前管理员。
3. 部门名称、父子关系、负责人和排序应正确保存，不允许形成循环层级。
4. 测试用户的账号、手机号、邮箱等唯一字段应进行重复校验。
5. 测试角色可以配置最小菜单权限，保存后权限树回显一致。
6. 不实际登录新测试用户，不进行越权、安全攻击或密码猜测。
7. 自定义字段、编号规则和系统配置只允许新增 RUN_ID 测试项；不得修改已有生产式配置。
8. 操作日志应能记录本轮创建和编辑行为。

重点验证：

- 部门新建、编辑、父子层级和重名
- 循环上级校验
- 测试用户最小字段和完整字段
- 用户账号、手机号和邮箱重复
- 测试角色新建和权限树保存
- 用户绑定测试角色
- 菜单和按钮权限配置页面回显
- 自定义字段必填、唯一、默认值和排序
- 编号规则预览
- 系统配置页面只读检查
- 操作日志搜索和本轮行为记录

执行限制：

- 不删除、禁用、重置密码或调整当前管理员。
- 不登录新用户，不执行越权测试。
- 不修改已有角色、已有部门、默认菜单或全局编号规则。
- 对权限或系统配置的最终保存，只作用于名称带 RUN_ID 的新建对象。

## 模块 10：角色、菜单、按钮与数据权限专项

本模块对公共执行规则作以下补充：

- 权限配置必须由当前管理员完成。
- 权限验证必须使用专用测试用户，不能使用超级管理员验证，因为超级管理员可能绕过普通角色限制。
- 优先使用 Web Test 登录账号管理中保存的测试用户凭据。凭据不得以明文写入用例、截图或报告。
- 如果没有可登录的专用测试用户，先生成全部权限用例，只执行管理员侧配置检查；跨账号验证标记为“登录或权限阻塞”。
- 不得退出当前管理员会话，除非已经确认管理员账号可以安全恢复登录。

测试对象：

1. 使用 RUN_ID 新建或复用以下专用对象：
   - RUN_ID_权限角色A
   - RUN_ID_权限角色B
   - RUN_ID_权限用户A
   - RUN_ID_权限用户B（数据范围测试需要）
   - RUN_ID_部门A
   - RUN_ID_部门B（数据范围测试需要）
2. 权限用户只能绑定本轮 RUN_ID 角色，不得绑定超级管理员或已有高权限角色。
3. 如果上述对象已由人工准备，先核对名称、状态和权限，不要重复创建。
4. 用测试用户A和B分别创建一条 RUN_ID 线索和客户，用于本人、本部门和跨部门数据范围验证。

业务需求：

1. 管理员可以为角色配置一级模块、二级菜单和具体操作按钮权限。
2. 未获得一级模块权限时，用户不应看到顶部模块入口。
3. 获得一级模块但未获得二级菜单权限时，模块可以进入，但对应菜单不应显示。
4. 仅有查看权限时，用户可以打开列表和详情，但不应看到新建、编辑、删除、导入、导出、转移等未授权按钮。
5. 给角色新增按钮权限后，测试用户重新登录或刷新权限，按钮应出现且实际操作成功。
6. 撤销按钮权限后，按钮应消失；撤权前已经打开的旧页面也不得继续完成未授权操作。
7. 菜单和按钮的显示状态必须与实际操作能力一致，不能出现“按钮显示但点击后无权限”或“按钮隐藏但仍能从其他正常页面入口执行”。
8. 权限变更重新登录后必须稳定生效；若产品支持在线刷新，也要验证合理时间内生效。
9. 绑定多个角色时，菜单和按钮权限应按系统规则合并；移除一个角色后只保留其余角色权限。
10. 仅本人、本部门、本人及下属、自定义部门和全部数据等数据范围，应对列表、搜索、详情、关联选择器、统计和导出一致生效。
11. 如果系统提供字段级权限，不可见、只读、可编辑状态应在新建、编辑、详情、列表和导出中一致。
12. 禁用角色、禁用用户或移除角色后，权限应按系统规则失效。

第一阶段：读取权限模型并生成矩阵

1. 进入系统管理的角色管理，读取当前版本真实存在的权限树。
2. 记录一级模块、二级菜单、业务对象、操作按钮、数据范围和字段权限。
3. 不根据其他 CRM 猜测按钮名称，必须以当前悟空 CRM 权限树和页面实际按钮为准。
4. 先生成“角色权限—页面表现”追踪矩阵，包含：
   - 权限点
   - 所属模块
   - 当前配置
   - 预期菜单状态
   - 预期按钮状态
   - 预期可执行动作
   - 预期数据范围
   - 关联用例编号
5. 对权限树中实际存在的按钮逐项生成用例。CRM 重点关注：
   - 新建
   - 查看
   - 编辑
   - 删除
   - 导入
   - 导出
   - 转移
   - 分配
   - 锁定/解锁
   - 放入公海
   - 领取
   - 添加团队成员
   - 新建联系人
   - 新建商机
   - 新建合同
   - 新建回款
   - 审批操作
   - 打印
6. 当前权限树不存在的权限点标记为“当前开源版本未提供独立配置”，不得伪造用例。

第二阶段：最小权限递增测试

按照以下阶段逐次修改 RUN_ID_权限角色A。每个阶段都必须保存角色，由权限用户A重新登录或刷新权限，再验证页面并截图。

阶段 A：无业务权限

1. 不授予客户管理模块。
2. 验证顶部“客户管理”入口不显示。
3. 验证通过站内导航无法进入客户管理页面。
4. 不进行接口构造或攻击性越权测试。

阶段 B：客户管理与线索只读

1. 授予客户管理一级模块、线索菜单和查看权限。
2. 不授予新建、编辑、删除、导入、导出和转移权限。
3. 验证：
   - 客户管理入口显示。
   - 线索菜单显示。
   - 未授权的客户、联系人、商机等菜单不显示。
   - 线索列表和有权数据详情可打开。
   - 新建、编辑、删除、导入、导出、转移按钮不显示或不可操作。
   - 快速创建中没有未授权的线索创建入口。

阶段 C：增加线索新建权限

1. 只增加线索新建权限。
2. 验证新建按钮和快速创建入口按设计出现。
3. 使用 RUN_ID 数据实际创建一条线索并刷新验证。
4. 验证编辑、删除、导入、导出和转移仍不可用。

阶段 D：增加编辑和导出权限

1. 增加线索编辑和导出权限，不增加删除权限。
2. 验证编辑、导出按钮出现且实际操作成功。
3. 导出内容只能包含当前数据权限范围内的数据。
4. 验证删除按钮仍不显示或不可操作。

阶段 E：撤销新建权限

1. 撤销新建权限，保留查看和编辑权限。
2. 在测试用户已经打开线索列表的情况下刷新页面。
3. 验证新建按钮和快速创建入口消失。
4. 如果撤权前已打开新建弹窗，通过正常页面尝试提交本轮数据，系统应阻止保存。
5. 验证已有线索仍可按保留的编辑权限修改。

阶段 F：撤销客户管理模块

1. 撤销客户管理一级模块。
2. 测试用户重新登录。
3. 验证顶部模块、二级菜单、快速创建入口和相关待办入口全部消失。
4. 其他已授权模块仍能正常使用。

第三阶段：多角色权限叠加

1. 角色A只授予线索查看。
2. 角色B只授予线索新建，不授予编辑、删除、导入、导出和转移。
3. 同时给权限用户A绑定角色A和角色B。
4. 验证用户最终拥有查看和新建权限，但没有其他操作权限。
5. 移除角色B并重新登录，验证新建权限消失、查看权限保留。
6. 再移除角色A，验证线索菜单按系统规则消失。
7. 如果系统不是权限并集模型，记录实际规则并分类为“需求与系统配置不一致”，不要直接报缺陷。

第四阶段：数据范围

数据范围测试需要权限用户A和B分别属于测试部门A和B，并各自拥有明确归属的 RUN_ID 线索和客户。

按当前系统实际提供的范围逐项验证：

1. 仅本人：A 只能看到自己负责的数据，不能看到 B 的数据。
2. 本部门：A 能看到测试部门A的数据，测试部门B数据不可见。
3. 本人及下属或本部门及下属：建立测试组织层级后，下属数据可见，平级和无关部门数据不可见。
4. 自定义部门：只选择指定测试部门，实际范围与设置完全一致。
5. 全部数据：只在专用测试角色上临时验证，不给已有普通角色增加全部数据权限。
6. 每种范围都验证：
   - 列表总数
   - 关键词搜索
   - 筛选结果
   - 详情入口
   - 关联业务选择器
   - 首页或商业智能统计
   - 导出文件范围（具有导出权限时）

第五阶段：字段权限（当前版本支持时）

1. 选择一个普通文本字段和一个联系方式字段。
2. 分别配置不可见、只读、可编辑。
3. 验证新建、编辑、详情、列表、搜索结果和导出中的表现一致。
4. 字段不可见时，不应通过页面其他区域、关联选择器或错误提示泄漏字段值。
5. 若当前版本没有字段权限，保存权限树和页面证据，分类为“当前开源版本未提供独立配置”。

权限专项用例必须额外包含：

- 角色名称
- 测试用户
- 授权前权限
- 本次增加或撤销的权限
- 预期菜单状态
- 预期按钮状态
- 预期操作结果
- 预期数据范围
- 是否需要重新登录

典型缺陷标题：

- 【权限】【线索】未授予新建权限，但列表仍显示“新建线索”按钮
- 【权限】【线索】撤销编辑权限并重新登录后，详情页仍可保存修改
- 【权限】【客户管理】未授予客户菜单权限，但快速创建仍显示“新建客户”
- 【权限】【数据范围】设置“仅本人”后，客户列表仍显示其他负责人的数据
- 【权限】【多角色】移除新建权限角色后，重新登录仍保留新建按钮

权限专项禁止事项：

- 不对超级管理员角色做减权、禁用或删除测试。
- 不修改已有角色、已有用户和已有部门。
- 不把“全部数据”或系统管理权限授予非 RUN_ID 用户。
- 不测试后台 API、参数篡改、接口越权或安全攻击。
- 不实际删除业务数据；删除权限只验证按钮、入口和最终确认前的权限拦截。
- 不执行导入；导入权限只验证入口和表单可达性。
- 导出只允许本轮 RUN_ID 数据或明确属于测试账号范围的数据。
- 完成后不自动删除角色、用户和部门，只输出清理清单等待人工确认。

## 模块 11：商业智能与全局只读回归

业务需求：

1. 商业智能应展示当前账号权限范围内的 CRM 和 OA 统计。
2. 日期、部门、员工、指标类型等筛选条件应正确影响图表、卡片、排行榜和明细。
3. 销售漏斗中的阶段、数量和金额应与本轮创建的商机数据一致。
4. 客户、联系人、合同、回款、产品和员工业绩等统计应与对应业务列表口径一致。
5. 图表下钻或明细列表不得丢失当前筛选条件。
6. 没有数据的时间范围应显示明确空态或 0，不得显示上一次筛选的旧数据。
7. 页面刷新、返回和切换模块后，筛选状态应符合系统设计。
8. 全局导航、快速创建、消息、搜索和常用页面应无白屏、404、502 或明显资源加载失败。

重点验证：

- CRM 仪表盘卡片
- 销售漏斗
- 业绩目标与完成率
- 员工业绩和排行榜
- 客户、产品、合同与回款分析
- OA 分析入口
- 日期、部门和员工筛选
- 图表下钻与明细合计
- 空数据和大金额/小数显示
- 浏览器刷新、前进、后退和深链接
- 顶部一级菜单和左侧二级菜单
- 快速创建入口
- 消息入口与未读数
- 页面控制台或网络中可见的 404、500、502、504

执行限制：

- 本模块以只读验证为主，不新增和修改业务数据。
- 统计预期只使用本轮已知 RUN_ID 数据和页面可核对的列表数据，不猜测数据库口径。
- 若历史数据影响精确统计，将结果分类为“环境或历史数据干扰”，并给出可验证的局部结论。

   - 风险与未测范围
   - 本轮 RUN_ID 数据清单
   - 发布建议
7. 不重新执行页面操作，不删除测试数据。
