# 项目优化演进状态说明

更新时间：2026-06-12

## 具体实现目标

把当前项目从一个“能运行的 AI 浏览器测试工具”演进成一个可长期迭代、可打包交付、具备产品护城河的 AI Web 测试工作台。

核心目标包括：

1. 建立稳定的 `Agent Loop`，让 AI 执行过程不再只依赖短期对话上下文。
2. 引入 `Visual Context Manager`、`Working Memory` 和 trace store，让视觉证据、工具调用、任务进度可以被持续追踪。
3. 建立结构化任务框架、覆盖矩阵、台账、步骤证据和最终报告，让运行结果能沉淀为可复核资产。
4. 处理长上下文压缩问题，让长任务在上下文接近上限时仍能保留目标、进度和证据。
5. 将运行时数据从 JSON 文件切换为 SQLite 数据库，支持桌面打包和本地持久化。
6. 继续向最终产品形态演进，形成区别于普通浏览器自动化脚本的能力壁垒。

## 已完成内容

### 1. 数据库切换

已完成：

- 新增 SQLite runtime engine。
- `sqlite-store.ts` 通过 SQLite 读写运行时数据，已替换旧的 `mock-store.ts` 历史命名。
- `prisma/schema.prisma` 和 `prisma/desktop/schema.prisma` 已切到 SQLite。
- 新增 `BrowserChatSession` 表。
- 新增 `SchemaMigration` 表，用于记录 SQLite runtime schema 版本。
- 新增 `SiteKnowledge` 表，用于沉淀站点登录方式、页面结构、可靠选择器、常见失败、业务概念和修复经验。
- browser-chat 会话不再写入 `browser-chat-sessions.json`。
- 删除 JSON store 同步、迁移快照和 atomic JSON 写入逻辑。
- 新增数据库备份、恢复、逻辑导出、逻辑导入 API。
- 存储健康面板现在显示 SQLite 数据库路径、大小、最近写入、schema 版本、备份状态、artifacts 边界和记录数量。

未完成：

- 尚未做桌面安装包的一轮完整真实机器验证。

### 2. 长上下文与结构化压缩

已完成：

- 增加结构化 context summary。
- 压缩内容包含目标、当前进度、后续行动、台账摘要和证据摘要。
- 长任务不再主要依赖原始历史回放，而是依赖语义状态继续推进。

未完成：

- 还没有对不同任务长度、截图数量、站点复杂度做系统压测。
- 还缺把压缩保真评分扩展到更多真实站点和长流程。

### 3. 任务框架、台账和报告

已完成：

- 支持根据用户需求生成 `taskFrame`。
- 支持在用例编辑器中修改任务框架。
- 运行步骤会携带 task frame、ledger items、working memory。
- 最终报告会使用任务框架、台账、步骤证据、截图链接和覆盖矩阵，并以正确 Markdown 格式展示。
- 报告生成后会自动产出质量评分、等级和复核检查项，用于检查覆盖矩阵、台账、问题复核、建议和上下文摘要是否完整。

未完成：

- 报告还缺多模板能力，例如冒烟测试报告、回归测试报告、竞品分析报告、验收报告。
- 还缺基于不同业务场景的 AI 二次复核和报告模板选择能力。

### 4. 运行页与证据展示

已完成：

- 运行页已展示结构化台账。
- 已加入 coverage matrix。
- 已加入 evidence index，并支持搜索和按类型/状态过滤。
- 步骤详情里已经展示步骤、工具调用、截图和台账之间的直接关系，因此不再额外展示 evidence graph。
- 执行记录页保留运行列表、回放、导出、删除和报告入口，不再展示跨运行趋势、失败聚类、flaky 分析或统计卡片。
- 最终报告弹窗已改为结构化展示，重点呈现结论、建议、问题风险、覆盖情况、步骤结论、截图证据和运行日志。
- 目标模式已加入“最小稳定性评测集”一键创建入口，覆盖 DOM mode、visual markers、长上下文压缩和 browser-chat 导出流程。
- 已将 report writer 与这些结构化数据打通。
- 运行页已加入报告质量面板，展示评分、等级、复核时间和逐项检查状态。
- 已新增 `getPageOverview` 只读浏览器工具，供 AI 在目标不清楚、页面内容密集或截图标记难判断时，先读取页面概览再选择点击/输入目标。

未完成：

- 还缺更深入的跨环境、跨账号、跨版本对比。
- 还缺围绕页面理解准确率、元素定位置信度、工具选择成功率和动作后验证的专项评测。

### 5. browser-chat 与实时状态

已完成：

- browser-chat 会话持久化进入 SQLite。
- 会话 API 已适配异步数据库读取。
- SSE 初始快照支持异步读取。
- 运行和 browser-chat 的实时状态更新链路已更稳。

### 阶段 C：护城河能力

目标：形成普通自动化脚本难以替代的产品优势。

建议方向：

1. 站点知识库：已支持沉淀每个站点的登录方式、页面结构、常见失败、可靠选择器、业务概念，并在后续运行中注入为策略记忆。
2. 测试资产沉淀：保留用例、运行、步骤、工具、截图证据、问题和风险的可查询记录，不再额外做关系图或独立证据面板可视化。
3. 自我改进闭环：失败后自动归因，沉淀 repair 经验，下次执行优先复用。
4. 行业模板：为电商、后台管理、SaaS、内容站、表单流程等场景提供模板化检查维度。
5. 结果对比：支持同一流程在不同时间、环境、账号、版本之间做差异分析。
6. 可解释报告：不仅告诉用户失败了，还能说明证据链、风险影响、复现路径和建议修复优先级。

## 对此前的总结

此前最重要的演进不是单个 UI 或单个 API，而是把项目的数据和执行模型从“临时过程记录”推进到了“可沉淀、可解释、可继续”的结构：

- AI 不再只是每一步临时看页面，而是围绕 Agent Loop、Working Memory、Visual Context Manager 和 trace store 执行。
- 长任务不再只依赖原始聊天历史，而是依赖结构化上下文摘要延续。
- 报告不再只是步骤列表，而是能结合任务框架、台账、覆盖、证据和质量评分，并以结构化界面展示给用户。
- 数据不再依赖本地 JSON 文件，而是统一进入 SQLite，具备桌面打包和长期本地存储基础。

现在项目已经具备“产品底座”，下一阶段的重点应该从继续堆功能，转向提升 AI 对浏览器内容的理解能力：更可靠地读页面、更准确地识别可交互元素、更稳定地选择工具，并在动作后及时验证页面状态。

## 风险与注意事项

1. 当前数据库中仍会把复杂对象以 JSON 字符串字段存储，这是数据库内部字段设计，不是运行时依赖 JSON 文件。
2. 截图、上传图片、Playwright trace、报告附件仍保留在文件系统中，这是合理的 artifacts 存储方式。
3. 旧的 `.data/store.json` 不再作为运行时来源；如果未来要兼容历史用户数据，需要单独做一次导入工具。
4. `sqlite-store.ts` 是当前运行时 store 入口，旧的 `mock-store.ts` 历史命名已移除。
5. 目前没有跑 `dev` 或 `build`，符合当前项目要求；本轮已用类型检查和 diff 空白检查验证。

## 下一步优先级

优先级建议：

1. 建立页面理解专项评测：同一页面同时记录 DOM 快照、可交互候选、视觉标记截图和 AI 选择结果，评估元素识别准确率。
2. 强化浏览器工具使用策略：为点击、输入、查找文本、读取 DOM、读取网络请求等工具增加置信度、失败原因和动作后验证。
3. 扩展站点知识库和探索模板库，把稳定选择器、页面结构、常见失败和修复经验注入后续执行。
4. 做桌面安装包真实验收，并继续打磨项目空间、模板库和失败恢复入口。
